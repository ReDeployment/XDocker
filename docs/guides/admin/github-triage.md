# GitHub 通知、问题处理与证据诊断

适用版本：包含历史补采集、问题处理、Release 与证据诊断的新版本 Admin。Release 回调同时要求新版 Webhook 接收器；发布和服务器验收记录见任务文档。

## 页面入口

登录 XDocker 后展开「研发协作 → 研发事件」。右侧使用纵向 Tab：

| Tab / 地址片段 | 看什么 |
| --- | --- |
| 待处理问题 `/#github/issues` | 按项目与 PR／SHA 归并 CI 失败、评论和审查证据；默认入口 |
| 项目检查 `/#github/projects` | 自动检查结果、PR、失败步骤与项目消息；手动操作收在高级操作 |
| 连接与接收 `/#github/hooks` | 只读连接状态、实时事件接收、容量和错误状态 |
| 通知收件箱 `/#github/inbox` | 原始通知及来源；已读只清除提示 |
| 发布记录 `/#github/releases` | Release、开发预发布、草稿及删除事件；不等于镜像验收通过 |
| 诊断记录 `/#github/diagnostics` | 已生成的证据报告；出现新证据后显示需重新核对 |

系统直接读取 GitHub API 与 Webhook，不读取 Gmail。截图里的机器人邮件对应 PR 评论、行内评论或审查事件，发布邮件对应 `release` 事件。

API 定时采集与 Webhook 导入是两个独立开关。API 轮询关闭不代表回调关闭；页面分别显示状态。网页每 5 秒只读取已保存数据，不自动重复补采集、诊断或状态保存。

## 自动更新与近期历史

管理员按 [只读连接步骤](github-connection.md) 配置两个 owner 的令牌并开启总开关后，后台自动首次补历史、收到事件后核对对应项目，并每 5 分钟补漏。关闭网页不影响采集；不需要日常逐个点击。是否启用以服务器的固定镜像身份、运行开关与实际采集结果为准。

### 手动补采集（排查用）

在「项目检查」找到项目，展开「高级操作」，点击「补采集历史」，输入完整项目名确认。返回「采集已提交」只说明请求登记，必须核对项目最终采集状态、时间和收件箱。

范围为最近更新的 10 个 PR（补历史时也读取已关闭 PR 的审查）、最近 30 条每类评论、10 个 Release，以及配置分支与最多三个开放 PR 的 CI。每次最多导入 100 条观察，超出的数量写在采集快照；首次自动补历史会继续补入剩余记录；手动补采集可再次执行。相同对象和相同内容去重，修改后的评论可形成新证据。观察去重记录达到 100000 条时拒绝新增对象，保留原记录。这不是完整 GitHub 历史审计。

显式普通 CLI 采集只生成基线通知；首次自动检查或显式补历史把窗口内评论等逐条补入。首次采集的 Release 快照仍可在发布页查看。分支名、短 SHA 和 tag 名不会猜成完整源码 SHA。

服务器采集使用 [观察指南](github-watch.md) 所述的 owner 只读凭据；本机 gh 登录不会自动传到服务器。无私有仓库权限、限流、分页缺失、超时或网络异常时保持未确认，不给出通过结论。

本机可以明确沿用现有 GitHub CLI，在私有目录验收：

```sh
python3 scripts/github-watch.py \
  --state /你的私有验收目录 \
  --project PowerX --gh --backfill
```

`--project all` 观察六个固定仓库。命令只请求固定 GitHub REST GET，输出采集状态，不输出令牌或评论正文；记录留在指定本机目录，不会自动进入远程控制台。

## 处理问题

1. 打开「待处理问题」。先核对项目、PR、完整 SHA、证据时间及「当前提交／历史提交／未确认」标记。
2. 点击「证据与处理」，阅读来源链接、评论正文及可用的文件、行号。机器人评论是待核对证据，不自动等于确定的代码 bug。
3. 选择「待处理／处理中／人工确认已解决／人工确认不处理」，填写至少 8 字说明，输入完整项目名，再保存。
4. 已读、处理状态和 CI 状态独立。「人工确认已解决」不会清掉失败检查或授权打镜像。出现不同的新证据时，已解决／不处理状态重新显示为待处理；旧说明保留。本地状态不会关闭 GitHub 的评论线程。
5. 并发页面或新证据导致版本变化时，保存会拒绝旧版本；重新读取再核对，不重复提交旧请求。

CI 事件按 SHA 分开。能识别的同一检查／工作流使用对象 ID 和尝试次数比较，不让较晚投递的旧失败覆盖新尝试；缺少身份或当前采集仍保持待核对。未绑定评论、历史 SHA、过期快照及未解决审查不能被当作当前提交已通过。只有新鲜完整的当前采集才提供当前 CI 信号；界面信号本身不是发布授权或 Actions 门禁。

问题归并读取最近 2000 条保存通知。已经打开处理、保存状态或生成报告的问题会另存证据，通知超出窗口或清理后仍可查看，标为旧保存记录并要求补采集复核。

## 生成只读证据诊断

在问题详情中输入项目名，点击「生成只读证据诊断」。报告记录项目、PR、SHA、证据版本、来源链接、已采集的失败 job/step、代码注解及评论提供的文件/行号，并列出下一步核对要求。

这是基于保存证据的报告，不是已执行源码分析的 AI 结论。代码根因无法从证据确定时明确写「尚未确认代码根因」。报告不下载任意链接、不执行评论或日志里的命令、不重跑 CI、不操作其他仓库，也不自动修复、合并或发布。需要核对源码时，把报告交给对应项目负责人在对应 SHA 上检查。

诊断只写 XDocker 本地记录，不请求 GitHub。新证据到达后旧报告标为需复核。最多保留 500 份报告；达到上限拒绝新增，不静默删除旧报告。

## 私有数据与部署

记录位于 XDocker 的 `data/admin/github/watch.sqlite3`，目录 700、数据库 600。新增表保存观察去重、问题处理状态、保留证据和诊断；不触碰 PowerX 业务库。评论与说明保存前脱敏，网页以纯文本显示，不渲染 GitHub HTML。

Release 接入需要同时发布新版 Admin 和 Webhook 接收器，再在六个既有 GitHub Webhook 的事件列表中追加 **Releases (`release`)**，保留原事件、签名 secret、URL 和 TLS 校验。只更新 Admin 不足以接收 Release。

部署前备份 Admin 私有配置和数据库。回退旧镜像保留新增表和记录；旧版忽略新表。若已配置 `release`，回退接收器时也恢复原事件选择。不要回滚覆盖仍在写入的数据库或复制本机验收库替换服务器库。
